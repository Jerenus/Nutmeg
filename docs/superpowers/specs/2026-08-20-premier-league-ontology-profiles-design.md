# 2026-27 英超联赛与球队本体画像设计

**日期：** 2026-08-20  
**状态：** 已确认，待资料实施  
**目标：** 用 Nutmeg 现有 `League` / `Team` 实体与证据式 `profile_notes`，为
2026-27 英超联赛及官方 20 支参赛队建立统一、可横向比较、可持续更新的赛季档案，
作为后续比赛判读的重要事实输入。

## 1. 背景与现状

Nutmeg 已有策展式实体层，但不承诺自动覆盖所有联赛和球队。当前实体种子包含
24 个联赛和 64 支球队；`eng-premier` 联赛对象存在，但没有画像笔记，且没有球队
以 `eng-premier` 作为 `competition_ids`。

本任务补齐英超的实体与资料，不新建另一套档案系统，不增加主观总评分字段，也不
把判断规则写进代码。可复用的事实沉淀到画像；当场有效的偏移判断仍通过 Read factor
表达，并继续接受 CLV 与 Brier 检验。

## 2. 采用方案

采用“原生本体 + 统一键体系”：

- `decision_entities_seed.json` 是可 review 的策展真身；
- `League` / `Team.profile_notes` 是运行时判读读取的唯一画像来源；
- `decision-entities-sync` 将种子幂等同步到 decision store；
- `decision-profile` 负责按联赛、球队或当日板面读取画像；
- `jczq_club_team_aliases.json` 只补官方 20 队实际需要的体彩中文别名；
- 不创建每队 Markdown 副本，不增加数据库或代码结构，不形成双份真相源。

## 3. 实体边界

### 3.1 联赛

更新现有 `eng-premier`：

- `name_zh`: `英超`
- `name_en`: `Premier League`
- `country`: `England`
- `season`: `2026-27`
- `aliases` 必须覆盖体彩板面可能出现的精确联赛名变体。

### 3.2 球队

以英超官方公布的 2026-27 参赛俱乐部名单为唯一边界，建立恰好 20 个 Team 实体。
每个实体必须具备稳定 `team_id`、中英文名、实际中文别名、
`competition_ids: ["eng-premier"]` 和完整画像。不得依据历史英超身份自动加入已降级球队，
也不得因资料不足自动造模糊实体。

## 4. 双层画像模型

画像分为稳定基线和动态状态。固定 key 使 20 队可按相同维度横向比较；每个 key 在同一
实体内唯一，后续通过较新的 `at` 更新，不堆同义笔记。

### 4.1 联赛固定维度

| Key | 内容 |
|---|---|
| `season_format_2026_27` | 赛制、欧战资格、降级名额及关键规则变化 |
| `result_baseline_2025_26` | 上季主胜/平/客胜与积分分布基线 |
| `goal_regime_2025_26` | 场均进球、大小球或高低比分结构事实 |
| `home_away_regime_2025_26` | 主客场差异及是否存在可复用的联赛级偏差 |
| `schedule_congestion_2026_27` | 国内杯赛、欧战和关键密集窗口 |
| `promoted_context_2026_27` | 三支升班马来源、升级路径及顶级联赛适应背景 |

### 4.2 球队稳定基线

| Key | 内容 |
|---|---|
| `strength_baseline_2026_27` | 上季名次、积分、净胜球及升班背景等客观实力底座 |
| `coach_system_2026_27` | 主帅任期、主要阵型、控球/压迫/转换等稳定打法 |
| `squad_spine_2026_27` | 门将、中卫、防守中场、组织核、终结点等阵容中轴 |
| `attack_profile_2026_27` | 创造方式、推进通道、终结依赖和定位球攻击 |
| `defence_profile_2026_27` | 防线高度、压迫、转换防守、禁区与定位球防守 |
| `home_away_profile_2025_26` | 上季主客场成绩与机制差异；升班马注明赛事层级 |

### 4.3 球队动态状态

| Key | 内容 |
|---|---|
| `summer_window_2026` | 关键引援、离队、租借回归及尚未关闭的转会风险 |
| `availability_2026_08_20` | 截止日的长期伤停、停赛、复出与参赛资格 |
| `cohesion_2026_08_20` | 首发连续性、主帅/体系变化、中轴换血与磨合阶段 |
| `watchlist_2026_08_20` | 会推翻当前画像的转会、伤愈、前三轮表现或赛程触发器 |

## 5. 横向比较口径

不建立脱离证据的单一总分。最终比较矩阵在同一组事实维度上给出可解释的状态标签：

- 实力位置：争冠、欧战竞争、中游、保级；必须同时列出客观底座；
- 阵容完整度：完整、局部缺口、中轴缺口、重构；
- 磨合阶段：稳定延续、局部换血、新体系装配、高不确定；
- 攻防结构：分别记录创造、终结、压迫、转换、防守中轴和定位球；
- 状态时效：稳定事实与 `2026-08-20` 动态截面明确分开；
- 风险触发器：列出需要在转会窗关闭、第 3 轮、第 5 轮重新核验的项目。

这些标签用于检索和人工比较，不作为自动偏移规则。`form`、连胜连败与榜位属于通常已在价内的
信息，只能作为状态描述，不能单独授权 belief 背离市场 prior。

## 6. 证据合同

### 6.1 来源优先级

1. Premier League、俱乐部、足总、欧足联等官方公告；
2. 官方比赛与赛季统计，或可复算的完整积分榜/比赛样本；
3. Reuters、BBC、Sky Sports 等可靠报道；
4. 可信的专业数据与转会来源，用于补充而非覆盖官方事实。

### 6.2 落库规则

- 每条 `profile_note` 必须有非空 `evidence` 和 `at`；
- 主帅、伤停、转会等关键动态优先使用官方链接；无官方来源时至少两源交叉；
- `evidence` 写出可定位的 URL、数据集或比赛样本，不使用“综合判断”作为来源；
- 事实与推断在 `note` 中明确区分，禁止把传闻写成已发生；
- 过期动态通过同 key 新日期覆盖，不能继续伪装成长期画像；
- 单场临场首发、临时轮换和未证实消息留给当场 Read，不沉淀为永久档案。

## 7. 数据流

1. 从官方英超名单核定 20 队边界与升降级变化；
2. 为联赛和每队按固定 key 建采集清单；
3. 先采官方身份、赛程、主帅、阵容和伤停，再补完整赛季统计与可靠报道；
4. 逐条交叉核验，形成带截止日的稳定基线与动态状态；
5. 追加编辑 `decision_entities_seed.json`，保留工作区已有的其他实体资料；
6. 补齐实际需要的中文别名，不改动无关映射；
7. 运行 `decision-entities-sync`，将种子幂等同步到 store；
8. 通过 `decision-profile --league/--team` 检查运行时可读性；
9. 运行别名解析、JSON、实体层测试和工作区差异检查；
10. 输出 20 队横向比较矩阵及下一次复核清单。

## 8. 更新节奏

- **资料截止：** 2026-08-20；
- **转会窗关闭后：** 更新 `summer_window`、`availability`、`cohesion`；
- **第 3 轮后：** 只核验新帅体系、首发连续性和重大结构洞是否真实；
- **第 5 轮后：** 用实际比赛样本更新攻防与主客场形态，但不以小样本直接覆盖上季基线；
- **之后：** 关键官宣即时更新；普通 form 留在比赛级判读，不滚入永久画像。

## 9. 验收标准

- `eng-premier` 有 6 个固定联赛画像 key，赛季为 `2026-27`；
- 官方 20 队恰好各有一个 Team 实体，全部挂到 `eng-premier`；
- 每队具备 10 个固定画像 key，且 `evidence` / `at` 均非空；
- 20 队没有重复 ID、重复规范名或冲突别名；
- 实力、完整度、磨合、攻防、主客场和风险触发器可在统一矩阵中横向比较；
- 种子 JSON 有效，实体同步幂等，League/Team 画像可由 CLI 读取；
- 英超相关中文名解析到正确 team_id，别名审计无已知英超漏点；
- 实体层相关测试通过，`git diff --check` 通过；
- 不修改决策逻辑、不新增自动评分、不覆盖工作区已有的其他实体资料。

## 10. 非目标

- 不在本任务内预测具体比赛或生成投注票；
- 不以赔率、EV 或价格倒推出球队事实；
- 不把 20 队画像写成自动 if/then 决策规则；
- 不承诺一次采集永久有效，动态资料必须按第 8 节复核；
- 不扩展到英冠、杯赛或其他联赛球队的全面补档。
